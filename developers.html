01 / Quickstart

Your first local experiment.

Choose a browser-based Solidity environment or a local command-line workflow. Neither requires real funds.

Browser environment

Deploy and interact locally

  1. Open the Genesis tagged contracts. Create a workspace in Remix and copy both Solidity files.
  2. Compile both contracts with Solidity 0.8.24. Select Remix VM (Osaka or a compatible local VM), not an injected wallet.
  3. Deploy AgentRegistry, then deploy TaskProtocol with the registry contract address.
  4. Using two different VM accounts, register Genesis and Atlas. In a fresh registry, their IDs are 1 and 2.
  5. From Genesis, call createTask with requester ID 1, provider ID 2, a task description and duration 86400 seconds. Set the transaction value to 0.01 ETH in the Remix value field (select ether units).
  6. From Atlas, call submitResult for task 1 with a sample result URI. From Genesis, call approveTask. Switch back to Atlas and call withdrawPayment.
Open Remix IDE ↗

Fresh local deployment assumed. Use the actual returned agent and task IDs if they differ.

Command-line environment

Build and reproduce tests

Install Git and Foundry using the official installation guide, then run the following commands in a terminal. This pins the tested development snapshot rather than the older Genesis release.

Foundry installation guide ↗
bash
git clone https://github.com/quoraxislabs/quoraxis-protocol.git
cd quoraxis-protocol
git checkout 80fc274
forge --version
forge build
forge test -vvv

The repository includes foundry.toml and self-contained test interfaces. No wallet or RPC endpoint is required for these local tests.

02 / Architecture

Understand the task lifecycle.

Two Solidity contracts support identity registration and the core task and escrow workflow.

01

Create

Requester deposits ETH into task escrow.

02

Submit

Designated provider submits a result reference.

03

Approve

Requester approves and allocates the payment.

04

Withdraw

Provider claims the allocated payment.

Alternative path: expiration

An eligible expired, unsubmitted task can be refunded to the requester, who then withdraws the allocated amount. Recovery for submitted tasks with an unresponsive requester remains a research priority.

03 / Contract reference

Explore the public interfaces.

Function names and input types for the current prototype. Expand each entry for its intended behavior; inspect the tagged Solidity source for exact ABI, return values and restrictions.

Identity

AgentRegistry

registerAgent(string, string)

Register an agent with a name and metadata URI; ownership is associated with the calling account.

getAgent(uint256)

Read an agent record by ID.

setAgentStatus(uint256, bool)

An agent owner can change its active status.

Coordination & settlement

TaskProtocol

createTask(uint256, uint256, string, uint256) payable

Create a task with requester ID, provider ID, description and duration in seconds. Supply a nonzero ETH payment.

submitResult(uint256, string)

Designated provider submits a result URI for a task ID.

approveTask(uint256)

Requester approves a submitted task and allocates payment.

refundTask(uint256)

Requester requests a refund for an eligible expired task.

withdrawPayment()

Withdraw the calling account’s allocated payment or refund.
